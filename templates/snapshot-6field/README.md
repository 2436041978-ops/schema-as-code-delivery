# 语义快照模板（6 字段，冻结 v1.0.0）

> 用 6 个字段，把"我觉得不对"变成机器能查的证据。
> 配套角色：设计师 / 产品经理（任何发现问题的人都可以填）。

## 这是什么

把界面上"不对劲"的直觉变成一条结构化记录：它会被机器接收、判定、归档，最终长成一条能自动拦截同类问题的规则。不需要会写代码，会截图、会描述困惑就够。

## 怎么填

| 字段 | 回答什么 | 合格线 | 典型不合格 |
| --- | --- | --- | --- |
| `snapshot_id` | 它是谁 | 组织内唯一，建议 `SNAP-年份-序号` | 留空、重复 |
| `scene` | 在哪个场景 | 精确到"哪个场景"，不是"哪个页面" | "设置页的报错" |
| `symptom` | 用户看到什么 | 引用界面真实原文，不转述 | "报错文案不对" |
| `impact` | 用户承受了什么 | 写清"用户因此做了什么错误决策" | "体验不好" |
| `expectation` | 本该表达什么 | 一句话，机器能据此判定 | "文案应该更严肃一点" |
| `evidence` | 证据在哪 | 至少 1 个真实产品实例（截图 + 复现路径） | "截图见附件"（无标注） |

四个字段的自问题（写不下去时各问一遍）：

- **scene**：换一个同事，只看这个字段，能十分钟内自己找到这个界面吗？
- **symptom**：这条快照半年后被人翻出来，原话还在吗？
- **impact**：用户看到它之后，是"必须立即处理"，还是"等一等就好"？这两个世界不能平均。
- **expectation**：只用一句话，机器能不能据此判断"实际表达"和"预期表达"是不是一回事？

## 完整示例

见 `snapshot-example.json`——BND-001「拒绝 ≠ 终止」：拒绝、终止、升级被 `blocked=true` 一个布尔值压塌成同一个槽位，修复路径是把 `boundary.soft / hard / review` 变成离散令牌写进契约。

## 常见退回原因

三条准入硬要求：格式硬要求（6 字段完整未改名）、语义硬要求（判断而非感觉）、证据硬要求（至少 1 个真实产品实例）。退回不是拒绝——退回时说明缺什么，补齐再进来。
