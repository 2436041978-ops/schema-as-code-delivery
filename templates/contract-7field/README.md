# YAML 契约模板（7 字段，冻结 v1.0.0）

> 用 7 个字段，把"绝对不能"变成机器执行的规则。
> 配套角色：设计系统负责人（及任何承担翻译能力的协作者）。

## 这是什么

把一条语义规则写成机器可校验、可编译、可追踪的契约。它不是文档，是接口——编译之后，它会变成 AI 生成工具的 Prompt 前缀、前端的 JSON Schema、设计师的走查 Checklist、流水线的 CI 规则。

## 怎么填（起草与评审同一把尺子）

| 字段 | 回答什么 | 起草时问自己 | 评审时看什么 |
| --- | --- | --- | --- |
| `intent_id` | 它是谁 | 它能被引用吗？ | 全局唯一、命名可读 |
| `description` | 管什么 | 一句话说清"管什么、为什么"吗？ | 是否从真实漂移案例来 |
| `version` | 哪个版本 | 初始版还是修订版？ | 版本纪律：语义不变更 patch / 令牌增删更 minor / 边界变化更 major |
| `semantic_domain` | 哪个域 | 管的是哪个域里的语义？ | 域已登记；一个契约只管一个域 |
| `applicable_products` | 在哪生效 | 全域通用还是特定产品？ | 范围宁窄勿宽 |
| `semantic_tokens` | 定义了什么语义 | 每个令牌都能在字典里查到吗？ | 只能引用已注册项，禁止自创（最严的一条） |
| `immutable_boundaries` | 红线是什么 | "绝对不能"的那句话是什么？ | 每条可机器判定，无"尽量/建议"类措辞 |

## 完整示例

见 `contract-example.yaml`——ERR-001 错误分级契约。评审时的三个硬要求对应核查：格式（7 字段完整）、语义（四个令牌均 registered，无自创）、证据（关联模式卡片 ERR-001 及其快照证据链）。

## 常见退回原因

- 令牌不在字典里："字典里查不到就先随手写一个"是这个体系最危险的苗头——先走 draft 通道注册（带 status/review_date），再回来起草
- 边界不可判定：机器是"合规即正确"，人是"意图即正确"——笼统要求"必须有确认"，机器会字面满足、语义偏离
- 粒度塞太满：一个契约只管一个语义域、一条漂移模式。拆成多条，而不是塞满一条
